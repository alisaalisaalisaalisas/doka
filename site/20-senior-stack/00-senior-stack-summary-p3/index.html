    🏁 20.S3 Senior Stack, Часть 3 — сводная проверка¶

    Кросс-тематический материал по Части 3: 20.12 Облака · 20.13 GitLab admin · 20.14 Rancher/k3s · 20.15 Виртуализация · 20.16 MySQL HA. Части 1-2: сводка 1 · сводка 2.

    Оглавление: 3.1 Сводные вопросы · 3.2 Сводные задачи · Что изучить дальше

    3.1 — 40 сводных вопросов¶

    Да/нет + почему (1-10)¶

    1. Можно ли считать GCP VPC «региональной», как AWS VPC?

    Ответ Нет: GCP VPC — глобальный ресурс, подсети региональные, маршруты между регионами работают автоматически. AWS VPC региональна; связность регионов — через peering/TGW.

    2. Достаточно ли IRSA для доступа пода в S3, если OIDC-провайдер кластера не создан?

    Ответ Нет: IRSA работает через обмен OIDC-токена SA на креды роли в STS; без OIDC-провайдера AWS не доверяет токенам кластера — поды получат NoCredentialProviders.

    3. Безопасно ли восстанавливать GitLab из бэкапа на новую версию?

    Ответ Нет: restore поддерживает только ту же версию (и тот же тип БД), что была при бэкапе. Сначала восстановить на старой версии, затем апгрейд по официальному пути.

    4. Является ли Rancher обязательным компонентом для работы k3s-кластера?

    Ответ Нет: k3s полностью самостоятелен. Rancher — management-слой (провижининг, RBAC, fleet); его падение не влияет на workload downstream-кластеров.

    5. Гарантирует ли semi-sync репликация MySQL отсутствие потери данных при failover?

    Ответ Почти, но не гарантированно: при таймауте ack (rpl_semi_sync_source_timeout) primary деградирует в async и продолжает коммитить. Нужен мониторинг статуса semi-sync.

    6. Верно ли, что LXC-контейнер в Proxmox — это то же самое, что Docker-контейнер?

    Ответ Нет: LXC — системный контейнер (полная init-система, общее ядро хоста, как «лёгкая VM»), Docker — процессный с immutable-образами. Разные сценарии: LXC — сервисы уровня ОС, Docker — приложения.

    7. Можно ли использовать Seconds_Behind_Source как SLI для репликации MySQL?

    Ответ Не стоит: метрика врёт при простое источника (показывает 0) и зависит от часов. SLI — heartbeat-таблица или сравнение GTID-множеств.

    8. Достаточно ли --tls-san только на первом сервере k3s?

    Ответ Нет: SAN должен быть в сертификате apiserver, к которому подключаются клиенты; при HA за LB — имя LB должно быть в SAN на всех серверах, иначе клиенты будут получать x509-ошибки после failover apiserver'а.

    9. Является ли NAT Gateway AWS точкой отказа egress для AZ, в которой он размещён?

    Ответ Да: NAT GW зонален. Если маршрут всех приватных подсетей ведёт к одному NAT GW, падение его AZ ломает egress этих подсетей. Правильно — NAT в каждой AZ + маршруты по зонам.

    10. Достаточно ли gitlab-backup create для полного восстановления GitLab?

    Ответ Нет: секреты (/etc/gitlab/gitlab-secrets.json) и конфиг вне бэкапа; без secrets — нерабочие CI-переменные/токены. Плюс restore только на ту же версию.

    Открытые вопросы «между подтемами» (11-20)¶

    11. Опишите путь «Terraform → Packer → Proxmox → k3s» для создания ноды кластера.

    Ответ Packer собирает шаблон VM (qcow2 с cloud-init, docker/k3s-пакеты) → Terraform (provider proxmox) клонирует шаблон с параметрами (IP, ресурсы, ssh-ключи) → cloud-init настраивает ОС → Ansible/k3s install скрипт поднимает ноду → нода регистрируется в кластере токеном. Всё версионируется в Git.

    12. Как связаны Cloudflare Tunnel и Zero Trust Access в схеме «внутренний сервис без VPN»?

    Ответ Tunnel даёт транспорт: cloudflared держит исходящее соединение к edge, домен указывает на туннель — открытых портов нет. Access добавляет identity-слой: перед приложением CF проверяет SSO-identity и membership в группе. Вместе: приватный сервис, доступный только сотрудникам, без VPN и открытых портов.

    13. Почему в AWS «поды получают IP из VPC» (VPC CNI) — это и плюс, и минус?

    Ответ Плюс: поды — первоклассные жители сети (прямая достижимость, SG на под). Минус: IP-планирование подсетей становится критичным (max-pods, префиксы), риск исчерпания IP, стоимость NAT для исходящего. Требует дизайна сети заранее.

    14. Сравните восстановление etcd (k3s), etcd (kubeadm) и GitLab — общий паттерн.

    Ответ Везде: снапшот/бэкап заранее + репетиция + остановка пишущих компонентов + восстановление данных + проверка целостности. Разница в деталях: k3s — cluster-reset с restore-path; kubeadm — etcdctl snapshot restore с --name/cluster; GitLab — restore + обязательные secrets. Общий враг — «первый раз на живом инциденте».

    15. Где в стеке MySQL HA место Orchestrator, ProxySQL и приложения?

    Ответ Приложение → ProxySQL (единый endpoint: write в hostgroup 10, read в 20) → MySQL-узлы. Orchestrатор наблюдает топологию, при смерти primary выбирает преемника и через хук двигает узлы в hostgroups ProxySQL. Приложение не меняет подключение.

    16. Как проверить, что Cloudflare действительно проксирует трафик (а не только DNS)?

    Ответ Заголовок cf-ray в ответе, IP-адреса ответа — из диапазонов CF (не origin), скрытие origin (direct-запрос к origin IP не отдаёт сайт), в CF-дашборде растут requests. Серое облако = только DNS: cf-ray отсутствует.

    17. Что произойдёт с fleet-бандлами при недоступности Git в Rancher?

    Ответ Уже развёрнутые bundle'ы продолжают работать (desired state применён); новые синки и дрейф-коррекция приостановятся со статусом ошибки в fleet. Кластеры не ломаются — GitOps деградирует до «последнего применённого состояния».

    18. Почему для k3s edge-кластеров часто отключают traefik и servicelb, и что ставят взамен?

    Ответ Встроенные компоненты минимальны: traefik ограничен в прод-фичах (middleware/наблюдаемость), klipper-LB не умеет ARP-анонс во внешнюю сеть как MetalLB. Взамен — ingress-nginx/traefik-прод + MetalLB (20.7), единый стек с остальными кластерами.

    19. Как связаны Packer-шаблоны и безопасность нод K8s?

    Ответ Шаблон = базовый hardened-образ (минимальные пакеты, CIS-настройки, containerd, ключи) — все ноды рождаются одинаковыми и соответствующими политике. Патчи = новый образ + перекат нод, а не ручные правки живых. Immutable-инфра на уровне хостов.

    20. Опишите роль DNS на каждом слое: Cloudflare → VPC-DNS → CoreDNS → под.

    Ответ Cloudflare: публичные имена (edge, proxy). VPC-DNS (Route53/Cloud DNS): приватные зоны — имена VM/LB внутри сети. CoreDNS: cluster.local (сервисы/поды) + forward внешнего. Под: resolv.conf → CoreDNS → forward → VPC-DNS → публичный. Каждый слой кэширует и имеет свою зону ответственности; петли между ними — классика инцидентов.

    Сценарии «что будет, если...» (21-30)¶

    21. ...удалить NAT Gateway AWS, не обновив route table приватных подсетей?

    Ответ Маршрут 0.0.0.0/0 → nat-xxx станет «blackhole»: приватные подсети потеряют весь egress (образы, apt, внешние API) при живом IGW-интернете у публичных. Классический тихий отказ — алерт на egress-доступность обязателен.

    22. ...GitLab-раннеру с executor=kubernetes дать ServiceAccount с правами cluster-admin?

    Ответ Любой job (и любой, кто может править .gitlab-ci.yml) получает cluster-admin: escape из namespace, чтение секретов кластера. Раннеру — минимальный RBAC в своём namespace; деплой — через GitOps/агента, а не kubectl из job'а.

    23. ...в k3s-кластере из 3 серверов одновременно перезагрузить два?

    Ответ etcd теряет кворум: оставшийся сервер перейдёт в read-only (записи отклоняются). После старта второго кворум вернётся. Если «перезагрузка» затянется и третий тоже умрёт — восстановление из снапшота. Планировать maintenance по одному.

    24. ...ProxySQL-правило ^SELECT → hostgroup 20 применить без исключения для SELECT ... FOR UPDATE?

    Ответ Транзакции с блокирующим чтением уйдут на реплику: FOR UPDATE на read-only узле — ошибка (или блокировка не сработает) → битые бизнес-транзакции. Правило FOR UPDATE → writer-hostgroup обязательно и раньше общего SELECT-правила.

    25. ...Cloudflare Access-политику для админки сменить с «email in team» на «everyone»?

    Ответ Админка станет доступна любому, прошедшему любой SSO (включая личные Google-аккаунты). Это не «открыть в интернет», но близко: identity-барьер формальный. Политики Access ревьюить как код (terraform provider) с обязательным review.

    26. ...Packer-сборка начнёт падать из-за изменения URL ISO у вендора?

    Ответ Конвейер образов встанет — и это хорошо: сломанный пайплайн лучше молча устаревшего образа. Чинить: обновить iso_url/checksum в Git (версионируется), прогнать сборку, перекатить ноды. Локальное зеркало ISO снимает зависимость от вендора.

    27. ...в Proxmox-кластере из 3 нод потерять кворум (2 ноды offline) и попытаться запустить VM?

    Ответ Proxmox заблокирует изменения (read-only cluster config) — запуск отклонён, чтобы избежать split-brain. Аварийно: pvecm expected 1 (осознав риск) или восстановить ноду/QDevice. HA-ресурсы не переедут без кворума.

    28. ...Orchestrator выполнит failover, но хук обновления ProxySQL упадёт?

    Ответ Топология MySQL переключилась, а роутинг — нет: записи продолжат идти в мёртвый primary (503/таймауты), новые primary простаивает. Хуки должны быть идемпотентны, с ретраями и алертом на расхождение «Orchestrator toplogy ≠ ProxySQL runtime servers».

    29. ...в EKS исчерпать IP-адреса подсети (VPC CNI)?

    Ответ Новые поды не стартуют (не могут получить IP): PodScheduled/ContainerCreating с ошибкой assign pod IP. Лечение: префикс-делегирование (/28), доп. подсети, переход на другой CNI. Профилактика: мониторинг доступных IP подсетей как SLI.

    30. ...запустить gitlab-backup restore на GitLab более новой версии?

    Ответ Restore отклонится (несовместимость версии/схемы БД). Правильно: поднять GitLab той же версии, восстановить, затем апгрейд по официальному пути. Отсюда правило: бэкап-документация фиксирует версию GitLab на момент бэкапа.

    Ловушки собеседований (31-40)¶

    31. «У нас всё в одном AZ — зачем нам NAT в каждой зоне?»

    Ответ Ловушка на понимание зонности: NAT GW зонален; его смерть = потеря egress всей AZ (обновления, образы, API). Экономия $32/мес против простоя деплоя. Плюс cross-AZ трафик до NAT другой зоны — платный.

    32. «k3s — это toy, для прода нужен kubeadm». Разберите.

    Ответ k3s — CNCF-сертифицированный K8s; «toy» — использование без понимания ограничений (edge-сценарии, SQLite, встроенные компоненты). RKE2/kubeadm выбирают для CIS-hardened enterprise. Вопрос не «toy или нет», а соответствие профилю нагрузки и зрелости команды.

    33. «Мы включили semi-sync — данные не потеряем никогда». Найдите дыру.

    Ответ Дыра — деградация: по таймауту semi-sync отключается и primary коммитит async (доступность важнее RPO по умолчанию). «Никогда» требует мониторинга Rpl_semi_sync_source_status и алерта на переход в async, либо жёсткой политики остановки записи.

    34. «Cloudflare скрывает наш origin — мы защищены от DDoS на 100%». Где утечка?

    Ответ Origin-IP утекает через: старые DNS-записи/сертификаты (censys/shodan сканят по сертам), исходящую почту с сервера, subdomain'ы без прокси, history DNS. Нужен firewall на origin (только CF-IP + origin cert) — иначе атакующий обойдёт CF напрямую.

    35. «Orchestrator сам всё починит — runbook не нужен». Что не починит автоматика?

    Ответ Orchestrator чинит топологию репликации, но не: расхождение данных (нужен checksum/sync), прокси-роутинг без хуков, приложения с закешированными подключениями, потерю semi-sync-гарантий. Runbook описывает проверку консистентности и коммуникацию, а не только failover.

    36. «VMware дороже — значит Proxmox везде». Что теряете?

    Ответ Зрелость enterprise-фич: живая миграция с shared-nothing, DRS-автобалансировка, экосистема бэкапов (Veeam), поддержка вендора для комплаенса. Для SMB/homelab Proxmox честно хватает; для регуляторных сред и огромных ферм — считайте TCO с рисками, а не только лицензию.

    37. «IRSA — это просто IAM-роль на ноде». В чём принципиальная ошибка?

    Ответ IRSA — привязка роли к ServiceAccount через OIDC: разные SA в одном поде-ноде получают разные права; креды краткоживущие и scoped. Роль на ноде (instance profile) = все поды ноды делят одни права — это антипаттерн, который IRSA и призван убрать.

    38. «Runner в K8s — это просто kubectl apply в job». Почему это архитектурная ошибка?

    Ответ CI-система получает kubeconfig кластера = компрометация CI = компрометация кластера. Правильно: pull-based (GitOps-агент/ArgoCD) — CI только коммитит в Git; либо отдельный «deploy»-кластер с минимальным RBAC и OIDC-привязкой.

    39. «MySQL репликация лагает — добавим ещё реплик». Почему не поможет?

    Ответ Каждая реплика применяет binlog своим (одним) SQL-thread'ом — лаг индивидуален и зависит от тяжести транзакций и I/O реплики. Новые реплики лишь добавят источников нагрузки на primary. Лечить: parallel replication, ROW-формат, разбиение тяжёлых транзакций, железо реплик.

    40. «Cloud-init — это про первый запуск, потом Ansible». Зачем тогда он в шаблонах, если Ansible всё равно гоняем?

    Ответ Cloud-init делает VM доступной для Ansible: hostname, сеть/IP, SSH-ключи, пользователь. Без него нет точки входа для конфигурации (bootstrap-проблема). Разделение: cloud-init = bootstrap (один раз), Ansible = конфигурация (повторяемо).

    # Шаг 1: что MetalLB назначил и анонсирует?
kubectl -n metallb-system logs ds/speaker --since=30m | grep -iE "announce|arp" | tail
#   "announcing IP 192.168.88.201 on eth0" — новый IP анонсируется ✅
kubectl get svc -n ingress-nginx ingress-nginx-controller \
  -o jsonpath='{.status.loadBalancer.ingress}'
#   192.168.88.201 (был .200)

# Шаг 2: отвечает ли новый IP снаружи кластера?
#   (с ноутбука в той же L2):
arping -c3 192.168.88.201
#   Received 1 response ... MAC 00:1c:14:xx  ← отвечает MAC ноды-лидера ✅ ARP работает
curl -m3 -sI http://192.168.88.201 | head -1
#   (пусто/timeout) ← ARP есть, TCP нет?!

# Шаг 3: где рвётся? Трассировка с ноды-лидера:
sudo tcpdump -i eth0 -nn 'host 192.168.88.201 and tcp port 80' -c 10
#   SYN приходит, SYN-ACK уходит — а клиент не получает → асимметрия маршрутизации!
# Диагноз: новый коммутатор настроен с другим native VLAN / ACL между портами —
#   SYN-ACK уходит в другой аплинк с stateless ACL и дропается.

# Шаг 4: обход и фикс
#   Обход (пока чинят сеть): закрепить старый IP за Service
kubectl -n ingress-nginx patch svc ingress-nginx-controller \
  -p '{"spec":{"loadBalancerIP":"192.168.88.200"}}'
#   + убедиться, что .200 снова анонсируется (speaker logs) и доступен.
#   Фикс сети: symmetric routing / вернуть native VLAN на аплинках.

    Проверь себя: curl -m3 -I http://<IP> отвечает 200 снаружи; kubectl get svc — EXTERNAL-IP стабильный; speaker-логи без ошибок анонса.

    Разбор: «MetalLB сломался» почти всегда = L2/L3-сеть вокруг: ARP-конфликты, VLAN-асимметрия, ACL. Методика: анонс (логи speaker) → ARP (arping) → TCP (tcpdump на ноде-лидере). Закрепление loadBalancerIP — легитимный обход, но IP должен жить в пуле и быть зарезервирован вне DHCP.
