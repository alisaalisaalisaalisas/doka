# 🎯 01. Топ частых вопросов и эталонных ответов на собеседованиях DevOps/SRE

## 🐧 Раздел 1: Linux и Системное администрирование

### В1: Что происходит при вводе команды `ls -la` и нажатии Enter?
> **Эталонный ответ:**
> 1. **Shell parsing:** Оболочка (Bash) считывает строку, разбивает её на токены (`ls`, `-la`), проверяет алиасы (`alias ls='ls --color=auto'`).
> 2. **Поиск пути:** Если `ls` не встроенная команда (built-in), Bash ищет бинарник по путям в переменной `$PATH` (`/usr/bin/ls`).
> 3. **Системные вызовы:** Bash вызывает `fork()` (или `clone()`) для создания дочернего процесса. Дочерний процесс вызывает `execve("/usr/bin/ls", ...)`.
> 4. **Загрузка в память:** Ядро выделяет адресное пространство, ELF-загрузчик считывает заголовки бинарника и подключает динамические библиотеки через `ld-linux.so` (`glibc`).
> 5. **I/O и VFS:** `ls` вызывает системные вызовы `openat()`, `getdents64()` (чтение содержимого каталога из файловой системы VFS) и `stat()` для каждого файла, чтобы прочитать его inode (права, владелец, размер).
> 6. **Вывод:** Программа форматирует текст и вызывает `write(1, ...)` в `stdout`. Процесс завершается через `exit(0)`. Родительский Bash считывает статус через `wait4()`.

### В2: В чем разница между Hard link и Soft (Symbolic) link?
> **Эталонный ответ:**
> - **Hard link (Жесткая ссылка):** Прямой указатель на тот же номер `inode` в файловой системе. Нельзя создавать для директорий и между разными файловыми системами. При удалении исходного файла данные остаются на диске, пока счетчик ссылок inode $> 0$.
> - **Soft link (Символическая ссылка):** Отдельный файл со своим собственным `inode`, внутри которого записан текстовый путь к целевому файлу. Может указывать на директории и файлы на других дисках. При удалении целевого файла ссылка становится «битой» (Dangling symlink).

### В3: Что такое Load Average и что означают три числа в `uptime`?
> **Эталонный ответ:**
> Load Average — это среднее количество процессов за последние **1, 5 и 15 минут**, которые:
> 1. Выполняются на CPU или ждут очереди к CPU (состояние `R - Running`).
> 2. Находятся в состоянии непрерываемого сна в ожидании I/O диска или сети (состояние `D - Uninterruptible Sleep`).
> *Оценка:* Если Load Average равен количеству CPU ядер, система загружена на 100%. Если LA выше числа ядер, а утилизация CPU низкая — узким местом является диск (Disk I/O Wait).

## ☸️ Раздел 2: Kubernetes и Контейнеризация

### В4: Что происходит, когда вы выполняете `kubectl apply -f deployment.yaml`?
> **Эталонный ответ:**
> 1. **Kubectl:** Валидирует манифест локально и отправляет HTTP POST/PUT запрос в `kube-apiserver`.
> 2. **API Server:** Аутентифицирует пользователя (Client Certificate/Token), проверяет права RBAC, прогоняет через Mutating & Validating Webhooks (например, Kyverno), сохраняет объект в `etcd`.
> 3. **Deployment Controller:** Видит новый/измененный Deployment через `Informer Watch` и создает объект `ReplicaSet`.
> 4. **ReplicaSet Controller:** Замечает нехватку подов и создает объекты `Pod` со статусом `Pending` (без привязки к ноде `spec.nodeName: ""`).
> 5. **Kube-Scheduler:** Видит неподжатые поды, применяет алгоритмы Filtering (фильтрация неподходящих нод по Taints, ресурсам) и Scoring (ранжирование), выбирает лучшую ноду и записывает Binding в API Server.
> 6. **Kubelet на ноде:** Получает событие о назначении пода на его ноду, вызывает CNI плагин для выделения IP и сети, вызывает CRI (containerd) для скачивания образов и старта контейнеров. После успешного старта обновляет статус пода на `Running`.

### В5: В чем разница между Liveness, Readiness и Startup пробами?
> **Эталонный ответ:**
> - **`startupProbe`:** Защищает тяжелые, медленно стартующие сервисы (например, Java/Spring Boot). Пока она не пройдет успешно, liveness и readiness пробы отключены.
> - **`readinessProbe`:** Определяет, готов ли под принимать трафик клиентов. Если падает — под исключается из `Endpoints` балансировщика `Service`, но **не перезагружается**.
> - **`livenessProbe`:** Определяет, не завис ли процесс в Deadlock. Если падает — `kubelet` принудительно убивает и **перезагружает контейнер**.

## 🌐 Раздел 3: Сети и Безопасность

### В6: Что такое TCP 3-Way Handshake и почему именно 3 шага, а не 2?
> **Эталонный ответ:**
> Шаги: `SYN` $\to$ `SYN-ACK` $\to$ `ACK`.
> Три шага необходимы для **двусторонней синхронизации начальных номеров последовательностей (ISN - Initial Sequence Numbers)** и подтверждения того, что обе стороны могут как передавать, так и принимать данные. Если бы шагов было 2, сервер не знал бы, получил ли клиент его `SYN-ACK`, что приводило бы к зависшим полуоткрытым соединениям при задержках в сети.

### В7: В чем разница между проксированием на L4 (TCP/UDP) и L7 (HTTP)?
> **Эталонный ответ:**
> - **L4 (Transport Layer):** Балансировщик (HAProxy/Envoy/NLB) работает на уровне IP и портов без анализа содержимого пакетов. Не может читать HTTP-заголовки, URL-пути, куки. Работает экстремально быстро с минимальным потреблением CPU.
> - **L7 (Application Layer):** Балансировщик (Nginx/Traefik/ALB) полностью расшифровывает TLS, парсит HTTP/gRPC запрос, может маршрутизировать по URL путям (`/api` vs `/static`), проверять JWT токены, сжимать gzip и вставлять заголовки `X-Forwarded-For`.

## 🎤 Deep Dive: как отвечают senior-кандидаты

### Формула ответа на технический вопрос

1. **Определение** одним предложением.
2. **Как работает** под капотом (syscall/протокол/алгоритм).
3. **Когда НЕ использовать** — границы применимости.
4. **Личный опыт:** «у нас это проявилось как…» — то, что отличает практиков от читателей Хабра.

### Быстрая самопроверка: вопросы-ловушки

| Вопрос | Ловушка | Эталонная мысль |
| :--- | :--- | :--- |
| Чем Docker отличается от виртуалки? | Не «легче», а механизм изоляции | VM — гипервизор+гость-ядро; контейнер — namespaces/cgroups общего ядра |
| Зачем нужен etcd, если есть Redis? | Не «обе NoSQL» | Raft-консенсус, линейная согласованность, watch — фундамент control plane |
| Как обеспечить идемпотентность деплоя? | Не «повторить пайплайн» | Desired-state модель: apply ≠ install; артефакты версионируются digest'ом |
| Что произойдет при потере кворума etcd? | Кластер не умрет сразу | API server перейдет read-only, планирование остановится, рабочие поды живут |
| Difference between `restartPolicy: Always` и liveness probe? | Это про разные вещи | restart — реакция kubelet на exit кода процесса; liveness — периодическая проверка здоровья |

### Поведенческие вопросы (STAR)

- **Situation:** контекст проекта и масштаб (RPS, размер кластера).
- **Task:** ваша конкретная роль.
- **Action:** решения + почему отвергли альтернативы.
- **Result:** цифры (latency −40%, деплой с 2ч до 8мин) и извлеченные уроки.

!!! tip «Красные флаги интервьюера»
    Избегайте: «мы всегда так делали», обвинение бывших коллег, незнание своих цифр («кажется, там было много серверов»). Говорите числами и компромиссами.

## 🧨 Типовые грабли Production

| Симптом | Причина | Быстрое решение |
| :--- | :--- | :--- |
| Кластер «деградирует» без видимых ошибок | Недореплицированные партиции/PG после отказа ноды | Проверить health/ISR/under-replicated до следующего сбоя |
| Латентность растет линейно с данными | Отсутствие партиционирования/индексов | Разбить по времени/ключу, пересмотреть схему |
| Бэкап есть, восстановления нет | Никогда не проверялся restore | Регулярный drill: restore в staging + checksum |
| После failover дубли/потеря данных | Настройки acks/consistency не осознаны | Зафиксировать гарантии записи в SLA сервиса |

!!! danger «Правило бэкапов»
    Бэкап — это не файл на S3, а **проверенный процесс восстановления** с известным RTO. Не проверенный бэкап = отсутствие бэкапа.
